# Quadrant Planner v1.0 Implementation Plan Index

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver Quadrant Planner v1.0 as a full architectural rewrite while preserving v0.x user data and the proven Windows/macOS packaging pipeline.

**Architecture:** Implement the approved design in seven ordered, independently reviewable plans. The sequence locks data/domain interfaces first, then pure decision engines, then desktop UI, planner UX, reporting, synchronization/backup, and finally hardening/release.

**Tech Stack:** Flutter 3.47.3, Dart 3.13.x, Riverpod 3.x, go_router 18.x, Drift 2.35.x, SQLite, Supabase REST/RPC, flutter_secure_storage, CustomPainter, excel_plus.

**Spec:** `docs/superpowers/specs/2026-09-30-quadrant-planner-v1-design.md`

## Global Constraints

- Windows and macOS are first-class targets.
- Flutter CI baseline remains `3.47.3`; Dart floor becomes `>=3.13.0 <4.0.0`.
- Local database is the source of truth; network must never block ordinary task work.
- Importance and current urgency use `0..100`.
- Default quadrant thresholds are `50 / 50`.
- Default workday windows are `09:00–12:00` and `14:00–18:00`; weekends are unavailable unless explicitly opened for a date.
- Only `planned` and `inProgress` tasks are Planner candidates.
- Automatic splitting is allowed only for tasks `>=60 min`, with chunks `>=30 min`.
- AI may rewrite weekly-report wording but may not invent facts.
- v0.x database must remain untouched after migration.
- Tokens must stay in OS secure storage, never Drift/SQLite, logs, or backups.
- Release artifacts are Windows x64 EXE and macOS DMG; DMG naming must not claim universal unless the binary is actually universal.

## Review Focus

1. Existing v0.x databases with unusual custom min/max ranges must migrate without clipping or destroying the source database — covered in Plan 01 migration tests.
2. Dates beyond bundled holiday data must still produce deterministic urgency/planning behavior instead of null/crash — covered in Plan 02 calendar fallback tests.
3. Dense/overlapping quadrants must remain keyboard accessible and clickable — covered in Plan 03 clustering/semantics tests.
4. Replanning must never move locked blocks or schedule across lunch/weekends — covered in Plan 04 schedule tests.
5. Sync/report/export failures must preserve local edits and drafts — covered in Plans 05 and 06 failure-path tests.

## Cross-plan interface locks

- Plan 01 owns persistent entities and repositories. Later plans do not bypass repositories with ad-hoc SQL.
- Plan 02 owns `UrgencyEngine`, `QuadrantEngine`, `PlannerEngine`, and work-calendar behavior.
- Plan 03 owns shell/router/design-system, global search, interactive quadrant UI, and derived task trajectories; it consumes Plan 01/02 interfaces only.
- Plan 04 owns editable daily plans and Focus sessions.
- Plan 05 owns `WeeklyReport`, weekly-note capture/history, style-profile import, and MD/XLSX/plain-text renderers.
- Plan 06 owns outbox/pull/conflict semantics, backup/restore, and JSON/CSV portability exports.
- Plan 07 changes no product semantics unless a defect requires a spec update.

Each plan ends in an independently testable commit series. Do not start the next plan while the current plan's targeted tests, full `flutter test`, and `flutter analyze` are failing.
